## 已确认：初版最小维护方案

2026-10-09，用户接受结合 M01–M03 收敛后的全部建议，确认记录先按现有 example 的方式组织，并授权 Agent 确定其他剩余业务约定。本模块采用“Agent 维护知识与关系，程序做必要业务校验并重建图”的分工。本节及下文执行契约为当前确认记录，迁入输入中与之冲突的旧候选以此为准。业务约定由 Agent 在用户授权范围内闭环，2026-10-10 获用户整体批准；后续推进沿用全模块 Design → 接入确认 → 正式 Prompt → Plan 的安排。

### 共用契约与主流程

- [M01](../01-runtime/design.md#runtime-contracts) 管理任务、预算、任务副本、版本、提交、编辑冲突及恢复。Agent 修改副本，校验后写回；M04 补齐自己的业务校验，不另设业务保存工具或知识任务状态机。
- [M02](../02-capture/design.md#capture-contracts) 提供长期只追加的来源队列。来源引用沿用 `{connector, session_key, line_start, line_end}`，行号从 1 开始、范围两端包含；不新增源消息 ID、不复制原文，也不另建来源定位协议。
- [M03](../03-episode/design.md#episode-model) 提供已关闭或因边界 / 来源纠错修订的 episode 及版本。关闭结果提交后由 worker 登记提取；M04 不裁定关闭，不定期巡检或批量重切分历史。

```text
取得关闭或修订后的 episode 及版本
→ Agent 按来源读取原文，搜索已有知识与关系
→ 判断新增、补充、修订或无需修改
→ 修改任务副本中的知识点与关系文件
→ 程序做业务校验，沿 M01 提交
→ 刷新名称定位与图索引
```

名称归一、知识粒度、关系是否重复和冲突解释由 Agent 结合已有记录与来源判断，使用清楚的规则与示例指导，不分别建立评分器或多阶段算法管线。没有值得保存的内容是正常成功结果，不要求每个 episode 产生知识点。

### 记录、名称与关系

知识点、关系分别以稳定 ID 定位独立 JSON 详情文件，名称用于检索和展示；正文先放在字符串中，不拆成 JSON 元数据与 Markdown 正文两份文件。2026-10-09，用户明确“先按照 example 的方式组织”，采用现有[知识点 example](../../knowledge-point.example.json)和[关系 example](../../relation.example.json)的字段分组，不再另建一套最小记录模板。

| 记录 | 沿用的组织方式 |
| --- | --- |
| 知识点 | `id / name / aliases`、`content`、关系引用、`provenance`、`observations / hypotheses / cognition`、`changes`；知识正文包含摘要、解释、条件与来源。 |
| 关系 | `id / name`、两端知识点、`kind / relation_type / direction_semantics / record_status`、`content`、适用时的 `analogy`、`assessment`、`provenance`、`observations / cognition`、`changes`。 |

组织方式采用 example，既有契约继续有效：知识点的 `relations` 保存独立关系记录 ID，不双份维护详情；会话来源采用 M02 队列行号引用，episode 关联保留在来源上下文 / provenance 中；跨关系假设保留外部引用，不复制正文。M04 定义知识内容、来源、关系端点及维护规则；认知、观察与假设字段由 [M05](../05-cognition/design.md) 定义，即使共用详情文件也不由 M04 重定义或覆盖。示例的具体值不作为必须完整填满每个分组的要求，空结果和未知状态按实际材料表达。

程序从记录派生名称到文件的映射，放在图外。同名异义使用带上下文的名称区分，如“调度器（vLLM）”；不因名称相同自动合并记录。改名保留稳定 ID，并在重建时更新名称映射与图，不增加独立改名迁移体系。关系名称结合两端知识点定位，映射返回实际关系文件引用，不只凭一个宽泛关系名称猜文件。

关系最少表达端点、名称、类型、方向含义、内容与来源。知识关系与用户联想分别表达；同一对知识点可以有不同关系，同一关系再次出现则追加依据，不因每次提及新增边。具体方向与定位采用下文执行契约，不建立庞大的预设关系分类表。

### 旧内容、修订与人工编辑

Agent 根据已有内容和新增依据综合维护。来源冲突先保留各自说法、适用条件和来源，无法判断时明确未决；普通会话提取不强制启动外部核查，外扩与资料核查沿 [M06](../06-expansion/design.md) 的职责处理。

episode 修订后，仅重新核对相关条目，修订失去依据的内容，保留其他来源仍支持的内容；不增加全图连锁自动修复。知识编辑复用同一维护与提交流程，保留用户修改和原因，后续维护考虑该依据。同期文件编辑冲突由 M01 处理，不新增逐字段锁定、编辑审批或自动合并机制。首次来源、更新依据和实质变化保持可回查，具体历史版本复用 M01。

### 图重建与查询

图仅保存知识点 / 关系名称及连接，详情与认知状态从文件读取。初版在启动时，以及知识或关系变更提交后从详情文件全量重建名称映射和图；实际规模使重建明显变慢时再优化。图刷新失败记录错误，沿 M01 提交记录补建，不重跑已经提交成功的提取任务。查询不使用构建中的半成图，也不将未完成刷新说成已经包含最新修改。

先提供名称查找、详情定位、邻居与关系查询；语义相关性、排序与具体上下文交付由调用模块按其职责处理。路径算法、查询预算和更复杂的查询能力按实际调用需求设计，不预先铺设接口。MCP / HTTP 包装分别归 M07 / M08。

### 最小业务交接与校验

| 交接 | M04 定义的业务内容 |
| --- | --- |
| 维护任务输入与结果 | 输入 episode 引用及版本，或外扩材料、用户编辑；结果引用本次新增 / 修改的知识点与关系，允许正常空结果。任务身份、状态、错误和输出版本沿用 M01。 |
| 名称与关联查询 | 名称查找返回 matches，详情返回 record 与版本，一跳关联返回邻居及关系引用；具体格式见下文执行契约。 |
| 提交后的图刷新 | 从已提交记录重建名称映射和图，供后续读取；提交、回退和重试协议沿用 M01。 |

程序检查 JSON 与必要字段有效、记录身份符合共用约定、来源引用能够解析、关系端点与明确引用的记录存在，以及 M04 修改没有意外覆盖 M05 管理的字段。校验失败沿 M01 返回修正，不发布无效结果。知识是否值得保存、名称是否同义、类比是否成立由 Agent 判断并保留依据，不交给机械校验器裁定，也不为每种语义不确定性增加状态机。

<a id="knowledge-contracts"></a>

## 执行契约：用户授权范围内的 Agent 闭环

2026-10-09，用户授权“其他几项你也看着定吧”。本节补齐业务交接、关系方向、查询返回、必要校验和维护案例；复用 example 与 M01–M03，不引入独立保存服务、语义匹配算法或连锁修复系统。

### 身份、来源与关系方向

知识点放在 `knowledge/<id>.json`，关系放在 `relations/<id>.json`，目录均相对于 M01 数据根。ID 的生成、版本和历史沿 M01；改名只改名称，不改 ID。知识点名称在有效名称映射中唯一，同名异义由 Agent 用上下文区分。关系通过两端知识点与名称定位；同一端点组合、同一关系名称复用记录，确有不同含义时采用不同名称。别名允许对应多个知识点，程序返回候选列表，不按首项强行合并。

图的业务结构为有向多关系图，节点仅为知识点，每条有效独立关系对应一条连接；具体库和内部 edge key 后续选型。方向遵循 `source_knowledge_id → target_knowledge_id`，`direction_semantics` 必须说明含义：

| 实例 | 方向 |
| --- | --- |
| 先备知识 | 导数 → 链式法则，表示 source 是理解 target 的先备；`relation_type: prerequisite`。 |
| 因果或机制解释 | 原因 / 机制 → 结果 / 被解释对象，具体条件保存在正文。 |
| 类比 | vLLM batching → 项目任务调度器，表示参照概念 → 尝试理解的概念，不解释为因果或先备。 |
| 对称联系 | 只存一条关系，`direction_semantics` 写明“对称，存储端点不表达逻辑先后”；默认双向邻居查询可从两端发现，不再复制反向关系。 |

`kind` 区分 `knowledge_relation / user_association`；`relation_type` 为非空名称，不增加固定大枚举。`record_status` 取 `active / inactive`，省略时按 `active`；inactive 记录保留详情与历史，但不加入有效图。内容争议、错误联想或待核查本身不使记录失效，继续在 `assessment` 和正文中表达；是否属于用户理解证据仍由 M05 判断。

会话 `source_refs` 使用 M02 的 `{connector, session_key, line_start, line_end}`；需要关联 episode 时另保留 `episode_id`，不改变队列引用格式。外扩输入使用 M06 输出记录的固定版本及其来源，不伪造队列行号；外部来源的具体记录格式由 M06 定义并在其 Design 对齐。M04 保留原来源引用和核查依据，不仅保存一段外扩摘要。

### 维护任务的业务输入输出

以下是 M01 任务中的业务载荷，不另建任务 API。记录版本使用 M01 的可回查版本引用，固定输入不在运行中换成最新内容。

| 入口 | 输入 |
| --- | --- |
| episode 提取 / 重分析 | `episode_refs`：episode ID 与版本列表；`reason` 为关闭或修订，修订时附已有修订原因。只处理已提交的关闭 episode，读取其真实来源。 |
| 外扩维护 | `expansion_refs`：M06 已保存结果的 ID 与版本列表；其中提供候选知识、关系及来源依据，由 Agent 与已有条目综合。 |
| 用户编辑 | `record_kind`（knowledge / relation）、`record_id`、`expected_version`、`changes` 与 `reason`；changes 仅含本次编辑字段，允许直接修改名称和正文，版本冲突按 M01 返回，不强制覆盖。 |

维护结果采用 `{knowledge_refs, relation_refs, reason}`；两类 refs 均是本次实际新增 / 修改记录的 `{id, version}`，版本由程序提交后填写。未修改时两个列表为空，reason 说明“没有新增内容”或“已有记录无需更新”，任务可成功。实际文件变更集合仍由 M01 程序取得，不只信任 Agent 的列表。

结果引用可供 M05 读取受影响知识与关系，由 M05 判断是否更新认知；M04 不直接改写理解状态或安排递归重分析。用户编辑中明确提交的观察或理解纠错转交 M05，M04 编辑只维护内容、关系和来源。

### 名称、详情与一跳关联查询

逻辑查询复用已提交记录；任务内读取任务副本，前台查询读取已提交版本。名称和别名匹配只去除首尾空白、忽略大小写，然后精确比较，不增加模糊相似度阈值或向量检索。Agent 没找到匹配时可继续使用已有文件搜索工具。

| 查询 | 返回 |
| --- | --- |
| 名称查找 | `{matches: [{id, name, version}]}`，主名称和别名匹配均返回全部候选；无匹配为空列表。 |
| 详情读取 | 输入记录类别和 ID，返回 `{record, version}`，record 为对应 example 组织的完整记录；未知 ID 明确返回未找到，不用空正文代替。 |
| 一跳关联 | 输入知识点 ID 与 `direction`（in / out / both，默认 both），返回 `{knowledge_refs, relations}`；knowledge_refs 是去重的邻居 `{id, name, version}`，relations 每项包含 `{id, name, version, source_knowledge_id, target_knowledge_id}`。端点与版本从映射 / 详情取得，不作为额外图属性。 |

已存在但没有有效邻居的知识点返回两个空列表；未知知识点返回未找到。对称关系无论 in / out 都可从两端发现，返回仍保留文件中的端点。结果按 ID 稳定排序，不带掌握分数或语义相关性排名，默认不截断一跳结果。更深遍历与上下文选择归实际调用模块设计，不先增加深度、分页或数量配置。

索引未就绪或提交后的刷新尚未完成时，一跳查询返回索引未就绪，由 M01 补建；详情读取仍可读取已提交文件。不把失败当空邻居，也不悄悄返回旧图冒充新结果。M07 / M08 负责把这些逻辑结果转换为 MCP / HTTP 表达。

### 必要字段与校验范围

| 记录 | M04 必要字段 |
| --- | --- |
| 知识点 | 非空 `id / name`，`content.summary` 与至少一条可回查的 `content.source_refs`。`aliases / conditions / relations` 等没有内容时允许为空或省略，不要求填满 example 的认知分组。 |
| 关系 | 非空 `id / name / source_knowledge_id / target_knowledge_id / kind / relation_type / direction_semantics`，`content.statement` 与至少一条可回查的 `content.source_refs`；两端必须对应知识点。非类比关系可省略 analogy。 |

校验基于本次任务变更后的记录集合，使同一任务新增知识点及其关系可以一起通过。检查 JSON / 字段类型、ID 与文件定位一致、名称及端点组合不产生定位歧义、队列来源范围有效、实际引用存在。显式提供的关系 ID 必须引用与本知识点关联的关系；它只是可选定位入口，图从独立关系记录构建。

编辑现有记录时保留 M05 管理的 observations、hypotheses、cognition 及相关 provenance 子字段；未改变内容不创建无意义修订。M04 不校验未定稿的 M05 分析规则或固定状态量表。错误指出文件、字段和原因，交回 Agent 在 M01 剩余额度内修正；没有额外重试或异常状态机。程序只校验结构与引用，知识价值、同义匹配和论断正确性由 Agent 判断并保留依据。

### 维护案例与验证方向

| 情境 | 初版行为 |
| --- | --- |
| 同一知识新增解释或条件 | 复用知识点 ID，更新 content 并追加新来源和 changes；不因再次提及新增节点。 |
| 新旧来源冲突 | 正文保留各自说法、条件与对应来源；关系在 assessment 中表达未决，不以较新消息自动覆盖。 |
| episode 边界修订 | 找到来源关联该 episode 的记录，按修订版本重新核对；失去支持的正文说明当前依据不足。关系无继续维护依据时置 inactive，保留旧详情及修订原因；其他来源仍支持的内容继续保留。 |
| 用户改名或修改正文 | 保留 ID、修改原因与历史，M01 校验版本后提交；全量重建使新名称生效，既有认知字段保持原值，认知纠错交 M05。 |
| 无新增知识 / 图补建失败 | 前者是正常成功空结果；后者保留已提交详情并补建索引，不重跑 Agent 或把图失败伪装为空结果。 |

实施时永久检查只保护“来源 / 端点可定位、同一对知识点多关系不会丢失、M04 编辑不覆盖 M05 字段、重建后改名与 inactive 生效”这些稳定数据完整性约束，捕捉断引用、丢边与跨模块覆盖回归；M01 已覆盖的提交与恢复不重复建设。当前测试仅覆盖历史采集，不覆盖这些产品规则。上述语义维护案例和 Prompt 效果作为实际使用验收，不固化为逐句输出断言；本轮只做文档与合成示例的一次性检查，不新增测试代码。

### D03：知识点、关系与认知地图

#### 知识提取 Prompt 草案

> 从提供的会话材料中，提取值得长期保留的概念、机制、原理、方法及关系。

主要参考 Eigma 的长期学习价值与完整概念整理，辅以 LLM Wiki 的已有索引、名称归一和来源标记。其他项目机制比较与 Prompt 来源保留在文末。待解决：Q06 / Q07。

#### 关系作为独立数据资产与图索引

2026-10-05，用户提出图既帮助 AI 理解用户的知识边界，也帮助理解其思考习惯和思考方式。2026-10-08，用户确认存储分工：每条关系像知识点一样单独保存为一个文件，图中只保存节点和关系的名称，详情通过读取对应文件获取。

知识点文件、独立关系文件与图索引按上述分工维护。目录采用 `knowledge/<knowledge_id>.json` 和 `relations/<relation_id>.json`，相对于统一数据根；关系正文、来源、类比对应点及边界、内容核查、用户观察、假设引用与修订历史按 example 分组保留在关系文件中。知识点 example 已调整为关系 ID 引用，不双份维护关系详情。

图保留节点之间的连接结构，节点和关系的信息只保存名称。关系类别、类型、核查状态、用户状态、来源及正文等详情均从对应文件读取；此前在图中额外保存筛选属性的建议由本次决定替代。名称定位、同名区分、改名维护及关系方向采用前文执行契约。

读取链路为：当前任务定位相关知识点 → 图查询邻居与关系名称 → 定位并按需读取知识点、关系及相关假设文件 → 必要时回查 episode → 由相应模块形成带依据的用户理解判断。更新沿 M01 的任务副本、校验与提交流程执行，提交后按前文规则重建名称映射和图；索引补建复用提交记录，不另建恢复协议。

一条联想边可证明用户在该次情境中作出了何种联系，但不单独证明稳定思考习惯。跨 episode 的多个关系记录可共同支持“用户倾向借助熟悉的工程机制理解新问题”等理解假设，同时保留其他解释、反例及适用条件；优先复用既有假设记录，不把这种跨关系判断复制到每条边。AI 提供类比、用户沿用类比和用户主动提出类比分别保留来源。多次观察支持同一关系时追加证据与变化记录，不因每次提及都新增一条平行边。

[关系模板（合成示例）](../../relation.example.json) 按用户要求展示 vLLM batching 与项目任务调度器之间的联想。`content` 与 `analogy` 保存具体联系、对应点和边界，`assessment` 表达关系内容的核查状态，`observations` 与 `cognition` 保存用户表现及理解判断，`provenance` 和 `changes` 保留来源与更新历史。示例的具体表现、日期及引用均为合成数据；关系仍待核查，不以助手解释证明知识关系成立。跨关系的思考习惯通过外部 `hypothesis_refs` 关联，不复制假设正文。

关系模板中的 `kind`、`relation_type`、`record_status` 和核查状态等保存在详情文件，不写入图索引。`record_status: active` 仅表示记录在用，不代表内容正确或用户掌握。知识关系使用 `kind: knowledge_relation` 与相应关系类型，可省略仅用于类比的 `analogy`；没有用户表现时观察列表为空、理解状态保持未知。M04 必要字段与定位已由前文执行契约定义，认知字段继续由 M05 对齐。

#### JSON 与 Markdown 的分工

用户询问知识点与关系模板适合使用 JSON 还是 Markdown。2026-10-09，用户接受初版最小方案：当前采用独立 JSON 详情文件，正文使用字符串，Discussion 使用 Markdown 说明字段及设计取舍；随后确认先沿用现有 example 的记录组织。

| 需求 | JSON | Markdown |
| --- | --- | --- |
| ID、端点、类型、来源引用及图索引 | 结构明确，可直接读取并校验 | 需要额外约定元数据结构与解析方式 |
| 状态、观察、假设及修订历史 | 适合按字段维护 | 自由正文容易发生格式漂移 |
| 长篇解释、公式及人工编辑 | 长字符串和换行编辑较繁琐 | 适合连续叙述与知识页 |

当前知识点与关系是持续维护的结构化记录，自然语言正文可直接保存在 JSON 字符串中，必要时在字符串内使用 Markdown。暂不将同一条记录拆为 JSON 元数据与 Markdown 正文两份文件；当实际出现需要人工阅读、编辑的长篇知识页时，再讨论正文拆分或 Markdown 元数据头，以免提前增加同步职责。JSON 仅提供格式，字段约束、引用检查及更新校验仍需另行设计。


### Graphify 的图构建思路参考

2026-10-09，用户提出后续可以基于 Graphify 的思想重建图。本次只核对本机已安装的 `graphifyy 0.9.28` 构建源码与 Skill 中的流程说明，未运行 Graphify、安装依赖或开展集成。该参考作为后续选型输入，不表示已决定依赖 Graphify。

Graphify 将实体 / 关系提取与图构建分开，构建阶段读取结构化 `nodes / edges`，再执行图分析及输出。M04 可借鉴“结构化记录 → 确定性构建图”的分工：Agent 已维护知识点与关系，重建只读取已提交的记录，不再次调用 LLM 从正文推断关系。来源、核查状态与认知判断继续保留在详情文件，不将 Graphify 的边属性或推断标签全部搬入名称图。

本机版本的 [`build_from_json()`](/D:/miniconda3/Lib/site-packages/graphify/build.py:539) 默认创建普通 `Graph`，可选 `DiGraph`，并复制节点与边属性；它不直接满足 M04 的名称图与同一对知识点多种关系约定。后续可参考其构建分层，具体库及适配方式仍待选择。社区发现、中心性、可视化及增量缓存不作为初版重建的前置步骤；有明确调用需要时再引入相应能力。

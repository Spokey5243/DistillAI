## 已确认：Agent 直接修改产品数据文件

2026-10-09，用户明确“agent 直接有权限来修改文件即可，就像 codex 一样”。本项选择方案 C：后台 Agent 在任务中按需读取、搜索并直接新增或修改产品数据文件，复用执行层的文件工具；不要求先调用业务保存工具或只返回变更结果让 worker 代写。

| 数据 | 写入者与用途 |
| --- | --- |
| episode、语义边界缓冲、知识点、关系、用户观察、理解假设和理解状态 | 后台 Agent 直接维护，用于交流整理、知识检索和基于历史回复的认知更新 |
| 原始材料与采集 / 处理进度、任务状态和运行历史 | 采集与后台程序维护，用于来源保留、调度、重试和恢复；语义整理不覆盖原始材料 |

程序继续负责调度、来源与格式等必要校验、去重、历史回查及处理进度。文件写入成功、Agent 运行结束和任务完成分别判断；校验失败时不推进处理位置，交回 Agent 修正。校验、并发写入、中断恢复及图刷新契约继续在 Q15 细化。

2026-10-09，用户进一步认可[任务副本成功后写回](technical-proposal.md#文件版本幂等与崩溃恢复)：Agent 仍直接使用文件 / 命令工具修改文件，先修改独立任务副本，程序校验与检查同期编辑冲突后发布到原目录；失败恢复沿版本日志处理。原目录修改在成功写回后可见，不再把实时写入原目录作为这项保存方式的前提。

保存方式已获用户确认，M01 当前版本已批准；SDK / RPC 与相关工具注册属于明确延后确认的 Agent 接入事项，业务记录字段由各归属模块细化。

## 当前讨论：后台 Agent 的目录权限与简易沙箱

2026-10-09，用户提出把后台 Agent 的权限限制在 DistillAI 与用户设定的工作路径内，并明确选择“保留任意 Shell / Python 命令，同时设计进程级沙箱”，以及“添加工作路径后默认允许读写，Agent 可以直接修改其中的文件”。用户进一步确认权限收紧立即生效、允许自由联网；本节采用方案 B，具体操作系统隔离实现继续调研，直接修改文件的既有决定继续有效。

### 允许路径及读写权限

初版建议将 DistillAI 的默认允许根明确为产品运行数据目录 `~/.distillAI`，设置 `DISTILLAI_HOME` 后采用该目录，不自动授予安装目录、源代码仓库或整个用户目录的权限。用户工作路径逐项配置；用户已确认添加路径后默认允许读写，Agent 可以直接读取、新建和修改其中的文件。是否提供单独的只读覆盖设置及其生效方式继续设计。

| 对象 | 建议权限与归属 |
| --- | --- |
| 产品派生数据，如 episode、边界缓冲、知识、关系与用户模型 | Agent 在授权范围内直接读写，沿用本文件已确认方向 |
| 用户添加的工作路径 | 默认允许读写，Agent 可直接修改其中的文件；未添加路径拒绝访问 |
| 原始采集材料与来源 | Agent 可按任务读取；由采集程序写入，语义整理不覆盖原文 |
| cursor、任务与处理进度、运行历史 | 程序维护，Agent 不直接改写；本地材料接管不使用 `.sent` 或上传锁，见 M02 |
| 权限配置、执行代码和凭证 | Agent 不能修改自身权限边界或执行代码；凭证不向模型暴露，配置仅提供任务所需的非敏感值 |

允许根与读写权限由程序 / Web 根据用户设置管理，权限配置受保护；Agent 不得通过修改 `config.json` 或新增工具、加载可执行扩展来扩大权限。原始 rollout 位于允许根之外时，由采集程序按既定流程送入材料目录或提供受限的来源读取结果，不为后台 Agent 开放整个 Codex 会话目录。

### 执行方式与取舍

| 方案 | 边界如何执行 | 取舍 |
| --- | --- | --- |
| A：受限工具（未采用） | 只注册经过统一权限检查的文件读取、写入、编辑、搜索及必要业务 / 外部检索工具，关闭任意 Shell、Python 执行和可绕过检查的工具或扩展 | 实现范围较小，但不满足用户已选择的任意命令能力 |
| B：进程级沙箱（已选择） | 在操作系统隔离环境内执行 Agent 的文件操作和所有命令及子进程，将允许目录、系统运行资源和必要网络能力明确授权 | 保留任意命令能力，并验证 Windows 上的进程、文件、凭证和工具兼容性 |

方案 A 的读写检查在工具真正执行前完成，不能只依靠 Prompt 或检查 Agent 当前工作目录；所有可访问本机文件的工具都经过同一权限判定。单纯限制 Shell 的 cwd 或过滤命令字符串不能替代方案 B。

方案 B 的约束覆盖实际执行文件访问的工具进程、Shell / Python 及其全部子进程，不能让文件工具在外部执行而仅把 Shell 放入沙箱。沙箱不继承后台程序的全部凭证与权限，必要的系统执行文件和运行库按只读运行资源提供；权限策略与执行代码由受保护的程序管理。用户已确认允许自由联网，不以指定模型 / 搜索工具或域名白名单作为产品限制；LLM 调用路径与凭证隔离仍待接入设计明确。联网权限不扩大文件与凭证访问范围。

路径检查需要按实际目标判断目录归属，处理 `..`、绝对路径、同名前缀、Windows 大小写及新文件的父目录；符号链接、junction 等重解析点与硬链接不能把写入转向越界或只读对象。解析检查与实际打开文件之间的目标替换也需在实现中处理，不能把一次 `resolve()` 当作完整隔离。路径无法验证时拒绝操作，并返回可定位的工具错误；不得自动扩大允许范围。Python 官方文档说明 [`resolve()`](https://docs.python.org/3/library/pathlib.html#pathlib.Path.resolve) 解析符号链接与 `..`，而 [`is_relative_to()`](https://docs.python.org/3/library/pathlib.html#pathlib.PurePath.is_relative_to) 只做字符串层面的归属判断。

Windows [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) 提供文件、凭证、网络和进程隔离，可作为方案 B 的可行性调查入口；尚未选定具体实现。Pi 的接入层和工具包装仍待核对，本项目尚未完成沙箱集成验证。

### 已确认：权限收紧立即生效

“权限收紧”指用户移除工作路径、缩小允许目录或减少读写权限，不表示程序自动修改用户授权。2026-10-09，用户选择立即生效：撤销旧授权时停止受影响的任务及其工具子进程，按新权限重建执行环境；不能仅更新配置而让旧进程继续使用已撤销权限。受影响任务不记为完成，取消后的恢复与文件回退交接继续细化。

“等当前任务结束后再收紧”的备选方案未采用。新增路径或扩大权限从下次任务生效仍是候选，尚未确认。权限收紧和失败回退的执行顺序、完成判定及恢复程序权限需要共同设计；Prompt 最后编写，不能用 Prompt 替代权限执行。

实施时的永久测试保护“授权路径内按权限执行，越界或权限升级被拒绝”这一稳定安全边界：覆盖路径穿越、同名前缀、链接目标、只读写入、权限配置自修改、旁路工具及子进程越界。它们用于发现将来的越权回归，现有采集验证不覆盖这项后台边界。真实 Windows 文件 / 链接操作、框架集成和页面授权流程作为环境验收记录；目前不创建测试或实现沙箱。

## 已确认：启动、优先级、预算与失败回退

2026-10-09，用户确认以下运行行为；具体接口与技术实现继续设计。

| 项目 | 已确认要求 | 仍需细化 |
| --- | --- | --- |
| 后台启动 | 插件初次调用时检查后台 Agent 服务进程是否存在；不存在则启动服务，存在则复用 | 服务身份与可用性检查、启动就绪交接、多个调用同时启动的去重、启动失败与退出规则 |
| 任务优先级 | 当前轮注入任务最高优先级，其他几类任务优先级相同 | 同级任务排序、执行名额、是否抢占及已运行任务处理；本项不改变 M07 的注入候选内容排序 |
| 运行预算 | 仅设置调用次数预算 | 计数对象、重试是否计入、任务额度及耗尽后的状态；模型上下文容量和底层运行超时与产品预算分别处理 |
| 失败回退 | 任务失败后恢复旧版本，覆盖 DistillAI 产品数据及 Agent 修改的用户工作路径文件 | 任务前版本定位、新增 / 删除 / 改名的恢复、并发用户编辑冲突、回退失败与崩溃恢复、取消及预算耗尽是否按失败处理 |

失败回退针对本次 Agent 的文件变更，恢复时需要保留用户或其他任务的独立修改；不推进失败任务的处理位置。任意 Shell / Python 也能修改文件，因此回退机制必须覆盖这些命令及子进程造成的文件变更，不能只对 Pi 的文件写入工具做备份。网络请求产生的远端变化不属于本地文件版本恢复范围。

## 共用接口与执行流程草案

2026-10-09，用户指出前述抉择点已有答案，要求进入下一步，并随后批准当前版本。本节将已确认行为落实为供其他模块引用的接口与状态基线。逻辑接口名表示职责；HTTP 契约见已批准的[技术方案](technical-proposal.md)，语言、框架函数签名及 Pi SDK / RPC 按[延后确认安排](#technical-selection)另行协商。

### 插件、MCP 与 Web 共用一个后台

| 逻辑接口 | 输入 | 返回及职责 |
| --- | --- | --- |
| `ensure_backend` | 数据根、客户端协议版本 | 后台实例标识、协议版本、就绪状态；插件检查并复用可用实例，不存在时协调启动 |
| `notify_materials` | connector 与 session_key，具体格式见 M02 的[通知契约](../02-capture/design.md#material-notification) | 提醒 worker 检查新增材料，不上传正文或要求 Hook 等待接收确认；worker 定期检查材料并轮询任务队列，通知失败可由扫描补登记 |
| `submit_task` | 任务种类、来源范围 / 记录版本、去重标识、关联 session / episode | 任务标识与状态；由 worker 登记、排队并执行，调用方不能自行指定越权目录或修改处理位置 |
| `get_task` | 任务标识 | 当前阶段、调用次数、结果版本引用、错误及恢复状态；模型返回与业务完成分别展示 |
| `cancel_task` | 任务标识、取消原因 | 取消请求的接收结果；终止工具子进程及文件恢复结束前，不宣告取消完成 |
| `read_config` / `update_config` | 配置查询；或修改值与预期配置版本 | 脱敏配置、生效值与待生效值；版本冲突或校验失败保留原配置，权限收紧走立即撤销流程 |
| `read_history` | 任务 / 记录 / 来源标识、筛选与分页条件 | 可定位的历史输入、输出版本、校验和恢复结果；M08 定义页面展示 |

后台身份按数据根区分，并校验协议与服务就绪状态；不能仅凭 PID 存在或端口有响应就认作本产品后台。并发调用 `ensure_backend` 只允许一个启动者，其余调用等待同一就绪结果；启动失败返回可定位错误，下一次调用可以重新检查。锁、进程身份验证及本机通信方式随平台选型确定。

Hook 和 MCP 连接退出不直接结束常驻后台。显式退出时先停止接收新的执行任务，再取消运行任务、处理恢复并保存状态；下一次插件调用按同一启动入口恢复。服务退出方式由 M08 提供交互入口，后台的控制接口不得对外网开放或让沙箱内任意命令获得控制权限；本机认证机制随通信选型明确。

2026-10-09，用户确认 M02 采用 Hook 同步落盘并通知 worker、worker 定期轮询任务队列的本地方案；后台直接读取持久材料，不维护 `.sent` 或独立上传确认。具体采集流程见 [M02](../02-capture/design.md#data-capture)。

M02 定义原始材料和本地通知的具体字段；M03–M06 定义各业务任务输入输出；M07 的实时筛选也通过同一 worker 登记，等待其结果，再转换成 Hook / MCP 返回格式。知识编辑和证据回写采用各自业务模块的接口，共用这里的任务、配置及保存机制。

2026-10-09，用户授权 Agent 补齐 M02 剩余执行契约；本模块同步引用其[材料 / 来源格式](../02-capture/design.md#capture-contracts)、[写入与尾部恢复](../02-capture/design.md#capture-write-recovery)和通知参数，不重复定义字段。来源行号从 1 开始且范围两端均包含，worker 只登记完整有效行；未提交尾部的修复不改变已登记来源。这里是已批准本地接管方向的接口细化，尚无 Plan 或实现需要调整。

### 来源、去重与任务范围

2026-10-09，用户确认采集采用[初版最小边界](../02-capture/design.md#minimal-capture-boundaries)：来源引用使用接入类型、session key 与持久队列行号 / 范围，不额外要求源消息 ID、turn ID、工具调用 ID 或原 rollout 定位字段。队列长期只追加，后台直接按引用读取，不再复制一份原文作为接收凭据；同一队列范围的重复通知复用任务。采集重试把同一正文追加到不同位置时，初版不承诺自动识别这种重复；产品记录与后台任务的自身 ID、版本及完成规则继续有效。

任务记录至少包含 `task_id`、任务种类、来源引用、输入记录版本、去重标识、关联任务、状态、调用计数、配置 / Prompt / 权限版本和输出版本引用。去重标识结合任务种类、实际输入范围 / 版本及触发事件；相同输入的重复通知复用任务，用户明确重分析则建立新任务并关联旧任务，不把历史输入改成最新值。

同一 session 尚未开始的有序增量可以合并；任务开始后输入范围固定，新材料登记为后续待办。收尾事件必须排在对应材料之后。M03 决定 episode 归属与关闭，调度器不以批次大小裁定主题；episode 关闭校验成功后，worker 接续登记知识提取，失败则不触发依赖任务。

### 排队、调用次数与状态

草案采用当前轮注入优先、其他就绪任务按登记顺序执行的规则；有依赖的任务在依赖完成后进入就绪队列。注入读取最近已校验的记录与候选版本，避免读到正在修改的半成品。注入不因普通任务正在等待模型而只能排在其后；具体执行名额与并发实现随调研确定，不仅给队列加优先级标签。

同一 session 的 episode 修改串行；对共享产品记录的写入和版本提交统一协调。任意命令的实际修改范围不能仅由 Agent 预先声明，因此用户工作文件的并发隔离与冲突处理必须由沙箱 / 回退方案提供，不能只依靠上述 session 排队规则。

调用次数预算的草案口径是：每次向模型服务实际发起生成请求前占用一次额度；工具执行和纯程序校验不计数，工具返回后的继续推理、校验修正与模型请求重试都计数。计数由程序维护，同一任务重试或后台重启不重置；已确定未发出的请求不计数，崩溃后无法确认是否已发出的请求保守计入。任务额度作为运行配置，具体初始值在技术调研后给出建议；不新增产品 token、时长或费用预算。

```text
queued → running → validating → succeeded
             ↑         │
             └─ 有额度且可修正的校验问题

running / validating → recovering → failed / cancelled
                                  → recovery_conflict
```

`succeeded` 必须同时满足实际文件结果保存、业务校验通过、输出版本及完成记录持久化。正常空结果也可成功，由业务模块给出“没有新增内容 / 没有匹配候选”的结果原因。运行异常、次数耗尽、用户取消、退出及权限收紧的草案处理是停止运行并进入恢复，不保留一个以后无条件续写的旧权限任务。

### 文件版本、完成与失败恢复

程序取得本次实际变更集合，覆盖文件工具、Shell / Python 及其子进程的新增、修改、删除与改名；每项保留任务前版本、任务产生的版本及路径。Agent 可提交结果引用，实际文件和引用校验仍由程序完成。模型会话日志不能替代变更集合；不能只对已知知识文件做备份而声称用户工作文件也可回退。

成功路径先校验并保存可回查的输出版本，再持久记录本次提交与可推进的处理范围，最后更新处理位置及派生索引。重启据同一提交记录补完尚未更新的位置或索引，不因模型曾返回成功而重做或越过材料；图刷新实现归 M04。校验修正期间处理位置保持不变，每次模型修正仍受剩余额度限制。

失败或撤销路径先停止整个工具进程树，确认不再写入，再由受保护的程序恢复本次 Agent 变更。权限收紧先禁止旧执行环境继续运行；恢复程序只处理该任务已登记的文件变更，不把旧权限重新授予 Agent。恢复后不推进失败任务的处理位置，后续重试在当前权限和配置下重新建立执行环境。

恢复不能覆盖用户或其他任务在本次运行中的独立修改。无法证明当前内容仅为本次 Agent 结果、恢复目标冲突或文件无法恢复时，进入 `recovery_conflict`，保留可恢复版本及错误，暂停冲突范围的后续写入，由 Web 展示差异供用户处理；不能宣告已回退，也不能静默强制覆盖。如何可靠捕获任意命令的修改、隔离并发编辑及完成跨文件提交，仍是[沙箱与回退专项调研](#technical-selection)必须解决的技术条件。

### 配置与历史交接

配置更新携带预期版本，程序校验后保存新版本；任务固定记录其实际使用的配置、权限及 Prompt 版本。普通模型设置和次数额度用于新任务，episode 参数按 M03 的 episode 生命周期应用；已有任务不在中途混用两套普通配置。新增路径或扩大授权建议用于新任务，收紧权限执行上述即时撤销。这里是生效规则草案，不把新增授权的候选记作此前已经确认的决定。

历史引用必须可定位当时内容，记录任务来源、模型可见请求与返回中需要核查的内容、工具结果摘要、实际文件变更、校验、完成与恢复结果；不要求存储模型内部推理。密钥、授权头及执行层凭证由程序排除，配置历史使用脱敏版本。M08 沿来源、任务和记录版本展开回查，不能用当前文件替代历史输出。

本轮接口与状态已纳入当前批准基线；永久验证应保护接收幂等、失败不推进位置、预算跨恢复不重置、权限立即撤销及回退不覆盖独立修改等稳定约束。具体沙箱集成、启动和崩溃窗口的环境验证在选型后落到 Plan，本轮只做文档一致性检查。

Web 保存请求由后台校验类型、取值和关联约束，再安全写入配置文件并返回结果；失败时保留原有效配置。页面展示当前生效值及待生效修改。普通业务配置的当前生效建议是模型配置用于下一次分析任务、episode 缓冲参数用于新 episode，已运行任务沿用启动时配置；具体生效规则、字段、默认值、读写接口和并发修改在 Q04 / Q15 中确认。权限收紧遵循[立即生效规则](#agent-sandbox)，不沿用这项普通配置建议。

这里的 Agent 能力包括理解材料、选择需要补读的上下文、调用工具查找已有记录，并根据结果决定如何整理和修订。一次模型调用能完成的任务可以直接完成；需要补读或核对的任务再进入工具调用与继续推理，不预设固定调用次数、多个 Agent 或每个职责独立服务。

**需要完成的工作：**

| 工作 | 输入与 Agent 需要作出的判断 | 预期输出与边界 |
| --- | --- | --- |
| 理解新增材料 | 新增用户、助手与工具材料及来源；识别讨论内容、用户表现、获得的帮助，以及缺失的背景 | 待整理内容和需要补读的来源；区分角色，不把助手解释或 AI 产物记为用户掌握 |
| 查找必要上下文与已有记录 | 当前概念、指代、原始消息、知识索引及相关假设；决定查哪些记录，是否需要继续回查来源 | 足以支持本次判断的材料与引用；允许跨 session 查找，避免无差别读取全部历史 |
| 构建与维护 episode | 当前活跃 episode、缓冲及有序新增对话；按 Prompt 判断连续性、评分并定位切换依据 | Agent 直接维护 episode / 缓冲文件，程序校验任务结果并推进处理位置；当前层级设计见 [D02](../03-episode/design.md#episode-model) |
| 提取与维护知识 | episode 关闭后由同一任务调度安排；读取该 episode 与已有知识，判断同义名称、重复内容、适用条件、冲突及观点变化 | 新增知识点或更新已有知识点及相关元数据，保留关系、来源与修订依据；不自行补足未讨论内容，具体记录见 D03 |
| 整理与维护用户观察 | 用户的主张、理由、解释、应用及帮助条件；判断值得保留的表现、相关旧观察和实质新增内容 | 有来源的观察及新增、补充或纠错建议；episode 的来源组织见 D02，观察的提取粒度另在 D03 / Q06 收敛，不预设每轮生成一份记录 |
| 建立与修订认知待验证判断 | 外扩候选及连接依据、既有用户表达与注入后的自然反馈；判断用户是否了解候选、是否建立相关联系，以及本次解释带来的帮助 | 关于用户认知的判断及来源、帮助条件和未决解释；具体记录与状态规则见 Q09 / Q10 |
| 按需处理查询与证据回写 | 当前任务的查询、候选知识与假设，或前台回写的纠错和新表现；判断相关性、来源条件与受影响范围 | 有来源的上下文或记录修订建议；查询是否需要实时 Agent 分析待定，日常提问与验证仍由通用 Agent 在任务中自然进行 |
| 核查本次分析结果 | 待保存候选及其原始依据；检查角色、来源、帮助条件、语义重复和前后矛盾 | 修订后的结果或明确的未决问题；没有值得保留的新增内容时可以返回空结果，格式正确不等于语义判断正确 |

外部知识扩展已由 Q01 纳入初版，流程方向见 D04；搜索工具与运行预算由 Q08 细化。

**工具需求与程序职责：**

| 能力 | Agent 如何使用 | 程序需要承担的部分 |
| --- | --- | --- |
| 读取与搜索 | 按来源定位消息或产物，搜索知识、观察和假设，再按需要展开正文 | 提供来源定位、范围筛选和读取结果；材料中的文本不成为覆盖应用规则的指令 |
| 关联查询 | 查询知识点邻居、相关假设、证据和受影响记录，解释查询结果 | 执行图查询并返回记录引用；图查询算法与记录标识不由 LLM 猜测，具体库后续选择 |
| 保存与修订 | 通过文件工具直接新增或修订产品记录，保留依据 | 校验字段和引用、关联来源、维护处理进度及恢复；原始材料不由语义整理覆盖 |
| 模型与工具执行 | 选择补读、查询、继续分析或结束，使用返回结果修订判断 | 执行层管理模型请求和工具调用；后台程序管理材料接收、调度、进度、锁、超时与失败恢复 |

用户已选择类似 Codex 的直接文件操作方式，后续按 pi-agent 的实际接入层复用读取、写入、编辑与搜索能力，并按[目录权限与沙箱设计](#agent-sandbox)限制访问范围。具体工具名称及命令执行能力随接入设计确定，不另行将业务保存接口作为文件写入前提。语义上的重复、冲突与关联由 Agent 分析，同一队列范围的重复任务通知由程序处理，两者不能互相替代。

**供框架与整体架构讨论核对的流程：**

```text
程序接收并定位新增材料
→ Agent 阅读材料，按需搜索旧记录与回查来源
→ Agent 核查依据并直接修改观察、知识与假设等文件
→ 程序检查任务结果；需要修订时向 Agent 返回具体问题
→ 文件已保存且必要校验通过后，程序推进处理状态
```

这是工作流程候选，不决定记录格式或调用轮数。模型返回成功不等于写入成功；后台离线、工具失败、并发更新及重启恢复继续由 Q04 / Q15 收敛。

选型时据此核对：模型 API 适配、工具注册与调用循环、上下文组织和结构化输出、异步执行与取消、可检查的调用结果，以及如何嵌入本地常驻后台并与 MCP 共用业务能力。哪些由框架直接提供、哪些复用本项目模块、哪些仍需编写，需要逐项确认；不把框架自带会话记忆等同于产品知识与用户模型的持久化。先明确任务范围、工具粒度、调用次数预算的计数口径、并发和恢复要求，再比较学习成本及二次开发工作量。

功能范围沿用 Q01 的确认结论，pi-agent 与 worker 分工沿用 Q04 的暂定方案。剩余模块与接口事项关联 Q04 / Q06–Q10 / Q12–Q15；episode 本轮讨论已确认，其激活、调度及上下文成本控制见 [D02](#episode-scheduling)，具体运行契约继续细化。框架与语言关注点见下节。

#### 后台 Agent 激活与任务调度

后台暂定以 pi-agent 作为可调用工具的 Agent 基础框架，通过 Prompt 指导 episode 构建与维护。后台程序常驻，任务调度由 worker 执行；在新材料或收尾事件到达时组织任务，调用执行层的 `prompt()` 或等价接口启动一次 Agent 运行，具体调用方式待接口设计确定。Agent 按需经历模型判断、工具执行与继续判断，完成后等待下一项任务。空闲等待和计时由程序承担，无需让模型持续轮询。

本层确认的处理链路为：

```text
接入端将新增材料落入本地队列，通知 worker 后返回
→ Worker 扫描持久材料并登记该 session 的未处理范围
→ Worker 定期轮询任务队列，安排待办任务
→ Worker 组织当前 episode、缓冲与新增材料的上下文，调用 Agent
→ Agent 按 Prompt 读取、按需回查、评分并直接维护 episode / 缓冲文件
→ 程序校验来源、顺序与任务结果
→ 保存及校验成功后推进处理位置，继续处理待办或等待
```

任务通知不等待模型分析完成，本地接管不设置上传确认或 `.sent`；模型运行结束也不等于业务保存成功。任务需指明来源 session、本次消息范围、活跃 episode、缓冲状态及材料位置，不把采集原文当作后台操作指令。SessionEnd 与空闲计时到期产生收尾任务，复用同一处理链路。

任务调度与执行由同一 worker 承担，包括安排运行时机与材料范围、组织上下文及调用 pi-agent，不额外构成两个 Agent 或独立服务。此前串行工作循环保留为候选；2026-10-09，用户提出协程或线程并发，具体实现留待[技术调研](#technical-selection)，不固定串行或线程方案。当前轮注入任务最高优先级，其他任务同级，见[运行规则](#runtime-decisions)。新增材料继续落盘，同一 session 不并发修改 episode；共享文件写入、任务状态与失败回退契约继续在 Q15 细化。

Agent 负责语义判断、选择必要上下文，并通过文件工具直接保存产品记录。程序负责来源与规则校验、去重、调度和处理进度；校验失败交回 Agent 修正。文件操作方式已由用户确认，具体规则、校验时机及恢复契约仍待细化。

后台 Agent 的运行会话与前端 session、episode 分别管理。业务连续性依靠持久化的 episode、缓冲与处理位置恢复，不要求把用户全部历史累计进一个无限增长的 Agent 对话。

pi-agent 基础框架与 worker 调度分工已暂定；Pi 接入可行性参考集中于 [运行选型参考](../../references/research.md#runtime-reference)，SDK / RPC 等接入方式尚未确定。

#### 调度与上下文成本控制

用户确认后续从任务调度和上下文组织入手降低后台 Agent 的 token 开销。调度器决定何时运行及一起处理哪些材料，上下文组织逻辑决定本次输入内容，初版可放在同一模块。优先合并同一 session 尚未处理的有序增量，减少固定规则、近期背景与旧材料的重复输入；合并的代价是处理延迟，积累量、触发时机与上下文组织继续细化。2026-10-09，用户确认产品运行预算仅设置调用次数，不把此前上下文预算候选作为已选的任务限额。

例如，固定规则与必要背景为 P，新增三轮为 A、B、C：逐轮调用可能分别输入 `P+A`、`P+A+B`、`P+A+B+C`；合并后一次输入 `P+A+B+C`，可减少重复输入及重复工具读取。这是说明优化方向的示例，不是已测得的节省比例；批量内仍按来源顺序识别边界，不把一批任务材料直接等同于一个 episode。

| 机制 | 解决的问题 | 边界 |
| --- | --- | --- |
| 调度缓冲 | 合并待办，决定何时调用 Agent，控制重复调用和等待时间 | 批量大小不固定等于三轮，不决定 episode 语义归属 |
| episode 边界缓冲 | 暂存疑似切换内容，利用后续对话确认实际边界 | 三轮是初始观察窗口，不要求调用模型三次 |

每次先提供当前 episode 的必要状态、近期原文与新增材料，更早历史按需读取；完整历史保持可回查，不要求每次推理全部加载。已在处理的范围不因重复通知重跑，新材料登记为后续增量。不同 session 分别组织任务上下文，避免无关历史持续累积；任务合并不得改变已确认的来源和 episode 边界规则。

2026-10-08，用户进一步提出在开放 episode 更新过程中定期准备相关认知子图：例如更新三次后，安排一次从完整地图检索并刷新子图的任务，供后续 MCP 上下文查询复用。子图准备可以发生在 episode 关闭前；关闭后的知识点提取规则继续保留。子图刷新与材料合并、语义边界缓冲是不同职责，具体交接与计数见 [D05：开放 episode 的相关子图与周期刷新](../07-context/design.md#开放-episode-的相关子图与周期刷新)。

与 vLLM batch 的类比仅用于理解统一安排工作：DistillAI 在业务层减少重复任务和重复上下文，vLLM 的 continuous batching 在推理层提高吞吐与资源利用率，不自动减少各请求的上下文 token 数。稳定规则与公共上下文可组织为前缀，以利用推理服务支持的前缀缓存；vLLM 的该机制复用 KV cache、减少重复预填充计算，与减少输入 token 数是不同优化，也不在本轮推定供应商计费收益。依据：[vLLM 功能说明](https://docs.vllm.ai/en/latest/)、[Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)。

#### 历史处理记录与回查

为支持 [本地 Web 行为核查](../08-web/design.md#local-web-console)，后台保留每次处理的模块与任务关联、实际输入范围及来源引用、输出或记录修订引用、执行状态、错误、耗时，以及当时生效的配置快照和可定位的 Prompt 版本。配置快照排除密钥；配置与 Prompt 版本需能回查当时实际内容，不能仅展示当前值。

引用可以避免重复保存原文，但须能定位当时的输入输出；源记录或派生内容后续修订后，仍能回查此前版本。Agent 运行结果、文件写入及程序校验结果分别记录，以区分分析完成、校验失败和持久化失败；没有候选、未注入等正常结果与错误分别表达。

这是历史回查需求，不预设全量复制模型上下文或记录模型内部推理。正式字段、文件组织、修订定位、保留范围及与处理位置的关联在 Q06 / Q15 中确定，历史记录不替代 D01 的采集、交付和后台处理进度。

## 已确认的初版上下文行为

2026-10-10，用户确认以下五项行为。其中每轮注入上限由建议的一条改为三条，compact 后明确重新注入；其余建议获接受。后台提前准备两个分别排序的列表、当前问题到达后由 LLM 筛选、SessionStart 恢复关联及入口规则、用户表现交回 M05，继续沿用既有方向。

### 首次准备与周期刷新

新 episode 首次成功保存后准备相关子图与两个列表；之后按包含新会话材料的成功更新次数周期刷新，重复交付或同一内容重写不计数。M03 明确切换到新 episode 时重新准备，不凭当前问题偏离主题自行切分 episode。具体刷新频率作为配置，三次更新仍是示例。

### 当前问题缺少相关资料

子图或候选没有当前问题需要的内容、首次准备尚未完成时，本轮注入返回空，不在注入路径临时展开完整检索和候选生成。MCP 查询先使用已有子图与上下文列表，缺少所需内容时允许按需扩大到完整地图，补查必要资料；不是每次查询都重查全图。完整地图仍无资料时返回无匹配，与服务不可用分别表达。

### 排序与本轮交付数量

MCP 优先提供与问题相关的背景和依据；注入优先提供与本轮相关、理解增量高且容易自然使用的建议。初版每轮最多注入三条，不要求凑满，没有适用条目时返回空；每条保持简短，详情可经 MCP 补查。两列表按用途定性排序并保留理由，不设计评分公式。

### 交付历史与 compact 后重新注入

保留交付历史，刷新候选不清空历史；同一建议默认不连续重复注入，内容实质变化或当前问题明确需要时可再用。交付、助手实际采用、用户接触与独立应用分别记录，不把交付当理解证据。

每次 compact 后，在续接当前轮前重新注入本轮已选素材，沿用已保存的选择与版本，不因之前已交付而跳过，也不重新执行 LLM 筛选；本轮已选素材仍最多三条。这是压缩后的上下文恢复，不算新增用户表现或新的选材。本轮没有已选素材时仅恢复入口规则。具体交付机制随接入对齐，并通过 Desktop 实测确认。

### 不可用与失败处理

后台、筛选或交付失败时，本轮继续正常回答，不带本次未成功交付的 DistillAI 素材，后台保留诊断；MCP 查询失败明确返回不可用，不伪装成没有资料。沿用已确认安排，不新增产品层筛选等待时限；平台或模型运行超时后按失败处理。任务预算、保存与失败恢复沿 M01。

#### 开放 episode 的相关子图与周期刷新

2026-10-08，用户明确：后台 Agent 在记录和更新开放 episode 的过程中，定期从完整认知地图检索相关子图，供后续 Prompt 上下文查询复用。例如，开放 episode 更新三次后刷新子图；中间的查询使用已有子图，减少反复检索完整地图的开销。三次是频率示例，尚未定为正式参数。

```text
新增材料 → 后台维护并保存开放 episode
                     ↓ 到达子图刷新时机
        结合 episode 的主题、目标及相关历史
                     ↓
        从完整认知地图检索并保存相关子图
                     ↓
        维护两个分别排序的列表
        ├─ MCP 上下文列表 → 助手按需查询
        └─ 注入 Prompt 候选队列 → 收到用户问题后筛选交付
                     ↓
        通用 Agent 围绕当前任务交互 → 新表现回写
```

这里有两种不同的检索频率：

| 动作 | 时机与范围 | 结果 |
| --- | --- | --- |
| 后台准备子图 | 随开放 episode 维护周期触发，从完整认知地图定位相关知识与连接 | 与本次交流相关的子图，关联该 episode |
| 按需取得上下文 | 通用 Agent 需要相关资料时，经 MCP 优先在准备好的子图内选择；资料不足时按需扩大到完整地图 | 少量知识、关系、扩充候选与相关用户状态 |

子图沿用图只保存节点和关系名称的规则；知识正文、来源、排序与用户状态读取对应详情文件。子图是交流相关内容的可重建视图，不另外复制一份权威知识或理解状态。子图中的外部候选仍保留候选身份，不因被检索或交付就成为用户掌握证据。

程序安排刷新时机并维护计数，后台 Agent 判断语义相关性并选择内容。2026-10-10，用户确认计数以成功保存、包含新会话材料的 episode 更新为单位，重复交付或同一内容重写不重复累计。周期子图刷新与 D02 的三轮语义切换缓冲分别计数，episode 更新次数也不直接等于用户轮数或 Agent 调用次数。

首次生成、新 episode 切换与缺少当前问题资料时的行为采用上节当前决定；具体频率、引用版本刷新与失效细节继续在 Q12 / Q14 / Q15 对齐。D04 面向知识扩展的主动全图扫描继续保留；这里降低的是日常上下文查询重复检索全图的频率。

#### 两个排序列表与本轮 Prompt 筛选

每次子图更新维护两个独立排序列表；子图更新准备候选，用户问题到达决定本轮交付。

| 列表 | 条目内容 | 排序关注点 | 使用方式 |
| --- | --- | --- | --- |
| MCP 上下文列表 | 知识、关系、用户习惯与表现、相关历史和扩充候选的引用及摘要 | 与 episode 的相关性、资料价值及来源状态 | 助手主动查询时，再按具体问题选择少量内容；列表较大不表示一次全部返回 |
| 注入 Prompt 候选队列 | 简短交互建议、关联知识/关系、适用条件与依据 | 连接价值、理解增量、当前需要与交互成本 | 问题到达后，筛选适用候选，再按优先级交付简短素材，每轮最多三条 |

两个列表可以引用相同的知识与关系，但各自评价用途。注入队列需要表达“在什么情境下，怎样自然引入这个连接”；它的条目包括使用条件和交互建议，知识正文继续保存在原文件中。两个列表与候选详情均在名称图之外维护，文件和正式字段待定。

推荐的交接如下：

```text
子图更新
→ 后台维护 MCP 上下文列表及注入候选队列，分别排序
→ 保留已交付记录，修订变化的候选，处理不再适用的条目

收到用户 Prompt
→ 接入端读取该交流可用的注入候选
→ 将用户 Prompt、必要交流背景及候选队列交给后台 LLM
→ LLM 筛选与当前问题相关、条件满足且适合本轮使用的条目
→ 在匹配条目中按优先级选择最多三条简短素材，不要求凑满
→ 通过支持的上下文入口交付；没有合适条目时返回空
```

候选队列按条件选择，允许跳过暂时不适用的高优先级条目。例如 e 的总体优先级最高，但当前问题围绕最大等待时间时，可以先选 c；未选的 e 保留供后续合适交流使用。优先级表达长期候选价值，本轮是否适用还取决于用户问题。

注入条目建议至少表达关联 episode 与知识/关系、Prompt 内容、适用条件、优先理由及交付状态。已交付、助手实际采用、用户接触与用户独立应用分别记录；不能仅因注入完成就认定掌握。子图刷新时保留交付历史，普通轮次的重复注入与 compact 后重新注入采用上节当前决定；具体字段与交付重试继续由 Q15 对齐。

收到当前用户问题后，读取后台提前生成的候选；完整检索和候选 Prompt 生成随子图更新提前完成。2026-10-08，用户明确收到问题后基于 LLM 筛选，等待时间暂不设置。后台 LLM 读取当前用户 Prompt、必要交流背景，以及带优先级和适用条件的候选队列，返回本轮选择的条目，或无适用候选的空结果；程序校验结果后交付对应 Prompt。

本轮交付使用支持的上下文入口，具体 Hook 候选及等待契约见 [T04](#injection-technology)。

2026-10-09，用户确认当前轮注入任务在后台调度中具有最高优先级，其他几类任务同级，统一规则见 [M01](../01-runtime/design.md#runtime-decisions)。任务调度优先级与候选素材的内容排序分别处理；执行名额及是否抢占仍待细化。

这里暂不增加产品层的筛选等待时间限制。Hook 配置和模型供应商的运行超时仍存在，超时或调用失败按上节失败处理；未准备好或没有当前问题的适用候选时返回空。正式筛选 Prompt、结果字段与版本校验、具体超时配置继续对齐。LLM 筛选使用已经准备的子图与候选，完整认知图谱的周期检索仍随 episode 维护安排。

#### 注入素材如何影响日常回答

后台筛选判断本轮是否值得交付，通用 Agent 组织回答时再判断是否实际采用。完整 Prompt 组合 Skill 的通用方法与本次素材，覆盖适用判断、自然使用和后续观察：检查任务相关性、突兀程度、理解负担及类比边界；适合时融入解释或例子，不适合时跳过。

交互方法和反馈解释集中于 D06，完整 Prompt 与分支见 C01。实际采用需有助手原文依据；没有用户回应不证明助手未采用或用户未理解，素材交付与用户独立应用分别记录。

#### 查询与证据回写

MCP 查询优先从较大的上下文列表及相关子图中选择少量材料，资料不足时按需扩大到完整地图，结果随工具返回直接进入上下文。主动素材交付与助手查询可以独立使用；外部知识搜索由后台按 D04 安排。

回写提交用户纠错、具体表现、来源与帮助条件，后台综合更新；一般会话仍由采集流交付，同源材料按来源关联去重，不能仅按文本相同去重。具体工具名称、数量和字段见 Q14 / Q15。

方法分工统一见 D06：Skill 提供交互方法，后台候选提供本次知识与用户证据。候选查询时机包括实质新任务、话题变化、引用历史或习惯及与已有记录冲突；现有资料足够时继续任务。

#### 启动上下文与 Skill 加载

Skill 默认按需加载，不保证安装后每轮执行；候选方式是在 `SessionStart` 给出核心规则并指向完整 Skill。LLM 可能漏查，具体触发与使用效果仍需在 Desktop 中核对。参考：[Codex Skill 加载机制](https://learn.chatgpt.com/docs/build-skills)。

##### MCP 使用提示的内容与作用

MCP 提示作为工具使用说明：当前任务需要用户习惯、历史、已确认边界或更多知识背景时，查询 DistillAI；现有上下文足够时继续任务；查询时说明要解决的问题，仅取必要资料。具体使用时结合来源和状态，用户当下指令优先于历史偏好。收到主动注入后仍可按需补充背景，调用 MCP 不作为采用注入材料的前提。

说明分三处承载：SessionStart 交付简短入口规则；插件 Skill 保存详细的查询、使用与回写方法；MCP 工具描述说明实际能力与输入输出。这里的“提示”指这些说明，是否额外提供 MCP prompt 资源继续按实际需要设计。提示引导模型选择工具，不自动执行查询或保证每轮使用，也不能代替 MCP 连接配置。工具名称、Skill 名称及路径尚未定稿，Prompt 应对应最终实际注册的能力。

查询优先从后台准备的较大上下文列表及相关子图中选择材料，资料不足时按需扩大到完整地图，返回内容与来源、事实或假设状态。查询工具的结果直接进入当前上下文；助手结合问题使用即可。回写工具可提交用户明确纠正、具体表现与帮助条件，后台综合更新；一般会话仍由原有采集流交付，Hook 与 MCP 的同源材料按 Q15 去重。

官方方法分工参考：[Skill 与 MCP 的职责](https://developers.openai.com/plugins/concepts/skills)。本项目的具体工具与 Skill 尚未实现。

##### SessionStart 触发后的处理

| 步骤 | 接入端与后台处理 | 交付或保存结果 |
| --- | --- | --- |
| 读取启动信息 | 读取 session_id、cwd、source 等 Hook 字段 | 确定本次会话与启动来源；当前用户问题由后续 UserPromptSubmit 取得 |
| 确保后台存在 | 插件初次调用时检查后台服务进程；不存在则启动，存在则复用，规则见 [M01](../01-runtime/design.md#runtime-decisions) | 后台启动就绪、可用性判定及重复启动协调待细化 |
| 关联会话 | 在后台登记或恢复同一用户、项目与 session 的关联 | 同一 session 重复启动保持幂等，不因 Hook 重触发新增 episode |
| 恢复已有工作状态 | 读取该 session 已保存的 episode 状态、子图与两个列表的关联 | 恢复已有记录；没有记录时保留未准备状态，episode 仍依据实际交流维护 |
| 交付启动规则 | 返回简短 MCP 使用提示与 Skill 入口，关联当前 session | 通用 Agent 获得资料查询及自然使用的方法 |
| 继续会话 | 用户新问题到达时，由 UserPromptSubmit 复用候选进入 LLM 筛选；compact 后直接续接当前轮时，重新注入本轮已选素材 | 启动规则与 compact 后恢复的已选素材进入续接上下文；本次启动不重新筛选具体素材 |

启动读取已有状态不要求调用 LLM 或重新检索全图；startup / resume / clear / compact 复用关联入口，保留 episode 边界、关闭状态及已交付记录。compact 可在没有新 UserPromptSubmit 时直接续接当前轮，每次 compact 后仍须重新注入本轮已选素材，不能因普通轮次的重复抑制规则跳过；具体交付与各 source 的恢复契约在 Q14 / Q15 对齐。压缩不自动推进理解状态。

后台不可用与首次子图尚未准备时的行为采用上节当前决定；启动登记方式与具体交付在 Q04 / Q14 / Q15 对齐，启动 Hook 实现候选见 [T04](#injection-technology)。

### T04：Prompt 注入与启动交付的实现候选

状态：`exploring`。

候选交付点为 UserPromptSubmit：接入端读取后台提前准备的注入队列，调用 LLM 按当前问题筛选，再校验并返回素材。功能契约见 [D05](#context-retrieval)，机制依据与调研边界见 [R04](../../references/research.md#prompt-injection-research)。

接入端建议使用同步 command Hook 等待这次筛选，再以 `hookSpecificOutput.additionalContext` 返回通用使用规则和选中的素材。根据官方等待与上下文契约，这条路径可以在当前用户问题发给模型之前完成交付；这是基于契约的可行性判断，当前采集插件尚未实现，也未通过 Desktop 实际触发确认。

官方确认 SessionStart 的附加上下文可进入模型上下文，输入不提供当前 prompt；MCP 类型 Hook 使用已有连接，且 SessionStart 可能早于连接就绪。因此建议启动采用本地 command Hook，直接返回规则及访问本地后台所需的初始化结果，MCP 连接就绪后再由助手按需调用。后台不可用与首次子图尚未准备时采用上节当前行为，启动登记与 compact 后重新注入的具体交付机制在 Q04 / Q14 / Q15 对齐。[官方 SessionStart 与 MCP Hook 生命周期](https://learn.chatgpt.com/docs/hooks)。这些实现候选尚未通过当前 Desktop 验证。


## Prompt 与验证的后续收敛

先确定本模块职责、输入输出、记录状态、异常与恢复，再参加全模块最后一轮 Prompt 讨论；正式 Prompt 写在本模块 Design 中，当前例子保留为候选。涉及跨模块的变更同步对应 Design，不复制另一模块的权威定义。

验收沿用 Discussion 的 Q02 / Q16。具体永久测试须保护稳定契约、来源和数据完整性或失败恢复；Desktop 触发、Prompt 效果和页面体验以实际使用验收记录。

## 批准与修订

2026-10-10，用户接受首次准备与刷新、资料缺少时的查询补查、排序与数量、交付历史与 compact 续接、不可用与失败处理五项行为建议，并明确每轮最多注入三条、compact 后重新注入；核对没有新增需要用户选择的产品问题后，用户明确批准当前版本。当前 Design 为 `approved`，决策方式为用户确认，`material_revision: 0`。

批准包含既定延后安排：MCP 查询与回写字段、候选及来源版本校验、交付记录和同源证据关联按已有契约补齐；具体接入与交付机制、正式 Prompt 后续确认，Desktop 实测尚未完成。按全模块设计 → Agent 接入确认 → Prompt 的顺序继续，尚未创建 Plan 或实施。实施后的实质变化按仓库 SDLC 规则记录决策方式及 Plan 影响。

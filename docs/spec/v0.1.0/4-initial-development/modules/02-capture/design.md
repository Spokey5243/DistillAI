#### 已确认的正文筛选规则

2026-10-09，用户确认助手中间消息、自动注入文本与非文本材料按 codex-honcho `c17cbb2b4c7cf12172213345ae4c0d2a093d707b` 的思路实现。本项替代此前非文本材料单独保存来源引用的决定。

- 只读取 `response_item` 中 `payload.type == message` 且角色为 `user` / `assistant` 的记录；独立 `reasoning` 记录不纳入正文。
- 保留助手中间文本与最终回答，不按 `channel / phase` 过滤。
- 字符串正文去除首尾空白；内容块只提取 `input_text / output_text / text` 的文本，按换行拼接后去除首尾空白；空正文跳过。图片、内嵌 base64 和其他非文本块跳过，不提取附件或专门保存其引用；文本正文已有的路径或 URL 作为普通文本保留。
- 仅对 user 消息进行注入前缀过滤：正文以 `<tag>` 或 `<tag ` 开头且 tag 为 `environment_context`、`turn_aborted`、`user_instructions`、`apps_instructions`、`plugins_instructions`、`skills_instructions`、`collaboration_mode` 之一时，跳过整条消息。未知标签及正文中间出现的标签不额外过滤。

实现依据：[正文解析与过滤](/E:/JourneyIntoAI/DL_and_LLM/projects/codex-honcho/src/transcript/codex.ts:34)。工具活动通过 `PostToolUse` 按下文规则单独记录。

#### 已确认的工具活动摘要规则

2026-10-09，用户确认工具活动记录初期采用同一 codex-honcho 提交的方案：由 `PostToolUse` 使用固定代码规则生成单行摘要，追加同一 session 的本地队列；不调用 LLM，不读取或保存 `tool_response`，不等待后台。执行方式遵循本模块已确认的同步 Hook / 异步 worker 分工，不照搬 Honcho 在 Stop 中等待上传的行为。

| 工具情况 | 摘要与过滤规则 |
| --- | --- |
| 工具名缺失或摘要为空 | 不入队 |
| 产品自身 MCP 调用 | 跳过自身查询产生的噪声；Honcho 以 `mcp__honcho` 前缀识别，DistillAI 对应自身 MCP 工具前缀，具体命名随 M07 接入契约确定 |
| `Bash / shell / local_shell / exec` | 从 `tool_input.command` 读取命令；数组按空格拼接，字符串直接使用，再去除首尾空白；空命令跳过。按参考实现 `TRIVIAL_SHELL` 固定表匹配完全相同命令或“前缀加空格”，如 `rg`、`cat`、`git status / log / diff` 等则跳过；其余记录 `ran: <命令前 120 字符>` |
| `apply_patch` | 从字符串 `tool_input.input` 或 `tool_input.patch` 解析 `*** Add / Update / Delete File:` 行；最多列出五个文件名，记录 `edited: <文件列表>`；无法识别文件时记录 `applied a patch` |
| 其他工具 | 记录 `used <工具名>` |

摘要条目沿用 `role: tool`、`text: 摘要`、`at: Hook 记录时的 UTC 时间`；通过 session key 和持久队列条目位置定位，不额外增加工具调用 ID。工具摘要不计入 rollout 正文消息的采集计数，但作为独立队列条目参与后台接管与处理。

实现依据：[固定摘要与跳过表](/E:/JourneyIntoAI/DL_and_LLM/projects/codex-honcho/src/hooks/observe.ts:14)、[工具条目入队](/E:/JourneyIntoAI/DL_and_LLM/projects/codex-honcho/src/hooks/observe.ts:61)。

<a id="capture-contracts"></a>

#### 执行契约：材料、来源与 cursor

2026-10-09，用户授权 Agent 直接确定本轮筛查剩余的四项执行契约并同步相关文档。以下为授权范围内的设计收敛，不改变初版最小边界；随后随 M02 当前版本获用户批准，尚未创建 Plan 或实施。

| 记录 | 正式格式与含义 |
| --- | --- |
| 队列条目 | `{role, text, at?}`；`role` 只取 `user / assistant / tool`，`text` 为筛选后的非空字符串。正文 `at` 使用源记录时间，能解析时规范化为 UTC ISO 8601，缺失或无效时省略，不用采集时间冒充源时间；工具 `at` 使用 Hook 记录时的 UTC 时间。 |
| 来源引用 | `{connector, session_key, line_start, line_end}`；初版 `connector` 固定为 `codex`。`session_key` 与队列文件名中的 key 一致；行号从 1 开始，范围两端均包含，单条记录的起止行相同。正文和工具条目共用物理行号，筛选子集保留原行号，不重新编号。 |
| 采集 cursor | `{count, at}`；`count` 为非负整数，表示已采集的筛选后正文消息数；`at` 为 cursor 保存时的 UTC 时间。缺失、读取失败或 count 非法按零读取；count 超出当前正文消息数时从头选取，沿用已确认的重采边界。 |

队列为 UTF-8、无 BOM、每条 JSON 后写一个 LF；正文中的换行由 JSON 编码转义，不产生额外物理行。写入者不生成空白行。worker 只登记已由 LF 结束、解析及字段校验通过的连续材料范围；未结束的尾部不取得来源行号，也不推进发现或处理位置。中段坏行保留原位置并报告错误，worker 不越过该行处理后续材料。

key 使用完整 `session_id`，仅将 ASCII 字母、数字、下划线和连字符之外的字符替换为下划线。不新增碰撞检测或回退标识。来源读取由后台根据 connector、session_key 和行号解析到统一数据根下的队列；来源引用不接受任意绝对路径或路径穿越。

<a id="capture-write-recovery"></a>

#### 执行契约：写入保护与未提交尾部

同一 session 的 Stop、PreCompact、PostToolUse 共用队列文件的单一系统级写入互斥。初版 Windows 使用原生文件句柄共享模式排除其他写入者、允许读取；互斥覆盖“读取 cursor / 确定增量 → 检查尾部 → 追加队列 → 保存 cursor”，句柄关闭或进程退出后自动释放。不新增上传锁文件或多层锁。获取不到写入权立即返回，由后续 Hook 补读正文；本次工具活动可能未采集，不承诺自动补回。

追加前先在内存完成条目编码。完整队列条目写入并执行文件 flush / 同步后，正文采集才通过同目录临时文件写入、同步及替换 cursor；工具摘要不修改正文 cursor。追加或同步失败不推进 cursor；cursor 保存失败保留已追加材料，下一次可能重采，按初版边界处理，不将两次文件写入称为事务。

rollout 未完成尾记录本次不计入采集计数，依靠后续 Hook 再读。对本地队列，worker 遇到未结束尾行先等待；下一位取得写互斥的采集写入者负责处理前一写入者留下的尾部：若尾部已经是完整且字段有效的 JSON，只补 LF 并同步；若尚未形成完整 JSON，仅截除最后一个 LF 之后、尚未登记或引用的尾字节，再正常追加。完整但字段非法的 JSON 报错并停止此次追加，不自动删除。所有完整来源行保持原文和行号，不修复中段坏行，不建立全文件自动修复体系。

这个恢复只处理从未成为材料条目的尾字节。若不能确认边界或文件操作失败，则保留文件、记录错误并停止本次采集；不强行截断。未完整落盘的工具摘要可能丢失，正文仍依靠后续 Hook 补读；文件同步不作为未经平台验证的断电完整性承诺。

<a id="capture-failure-behavior"></a>

#### 执行契约：缺失输入与失败返回

采集 command Hook 无论正常、跳过或失败，stdout 只返回 `{}`，退出码为 0，让 Codex 日常交互继续；诊断不混入 stdout。后台任务失败状态仍由 M01 管理，不把 Hook 返回成功解释为材料采集成功。

| 情况 | 采集端行为 |
| --- | --- |
| session_id 缺失、不是字符串或为空白 | 不创建队列或 cursor，记录诊断并返回，不生成替代 key。 |
| Stop / PreCompact 缺少 transcript_path 或无法读取 | 不追加正文、不推进 cursor，记录诊断并返回；不影响已存在队列由 worker 扫描消费。PostToolUse 不依赖 transcript_path。 |
| 工具名缺失、正文或摘要筛选后为空、没有新增正文 | 正常空结果，不产生材料条目；工具摘要按已有过滤表执行。 |
| 队列写入、同步或 cursor 替换失败 | 不提前推进采集计数，保留完整已写条目及可恢复尾部，记录失败阶段；不在 Hook 内重试或等待后台。 |
| worker 离线或通知失败 | 保留材料和 cursor，不等待恢复，不撤销写入，worker 启动 / 恢复 / 定期扫描时补登记。 |

诊断写入统一数据根的 `logs/capture-errors.log`，仅记录 UTC 时间、事件名、session key（可用时）、阶段和错误码；不保存原始正文、工具输入输出、凭证或完整异常 payload。诊断本身写入失败也不阻塞 Hook；后续补采仍取决于再次触发及源材料是否保留。

<a id="material-notification"></a>

#### 执行契约：轻量 worker 通知

复用 M01 已批准的本机 HTTP、实例身份及授权机制。`POST /v1/material-notifications` 的 JSON 请求体固定为 `{connector: "codex", session_key: "<key>"}`；不上传正文，不传文件路径或声称某个范围已接收。worker 校验 connector 和文件名 key，仅定位统一数据根中该接入类型已存在的队列，再自行扫描完整新增行并登记范围。

Hook 从既有实例信息取得后台地址和授权，通知仅尝试连接并完整写出 HTTP 请求；连接与发送共用 200 ms 的技术 I/O 截止时间，不读取或等待 `202` 响应，不重试，不启动后台或另起发送进程。实例不存在、失效或发送失败则跳过，可靠发现依靠 worker 扫描。后台返回的 `202` 只表达提示已收到；客户端未读取响应或已经断开，不改变材料扫描与任务恢复规则。服务端正常处理提示后忽略客户端断开造成的响应写入错误，不因此回退通知或重复登记任务。

worker 的材料扫描和任务轮询复用 M01 已批准的初始 1 秒间隔及 Web 配置；通知可提前唤醒同一消费入口。上述 200 ms 仅约束通知连接与发送，不引入 Agent 分析时长预算，也不要求采集 Hook 等待材料接收、任务登记或分析完成。

#### 后台职责

后台负责跨会话语义分析；采集材料保存、游标、同范围通知 / 任务幂等和恢复由程序处理，派生产品记录由 Agent 直接修改，见 M01 已批准的[任务、来源与保存契约](../01-runtime/design.md#runtime-contracts)。后台本地常驻，通过 API 调用模型；初期使用现有供应商，未来私有模型单独由 vLLM 服务部署。启动退出、任务调度及本地通信复用 M01；Agent 接入方式按全模块设计完成后的约定确认，MCP 业务工具由 M07 细化。

#### 已确认的采集与后台处理分工

2026-10-09，用户确认 Hook 通知 worker，worker 定期轮询任务队列并处理待办；本地后台直接消费采集 JSONL，不涉及向云端或另一份材料存储上传，因此取消 `.sent`。本项替代 2026-10-04 Honcho 参考方案中的独立交付确认，保留采集与处理解耦。

| 阶段 | 记录与推进条件 | 含义 |
| --- | --- | --- |
| 已采集 | 追加 `<key>.jsonl`，并更新 `cursors/<key>.json` | 材料已从 AI 工具读取到本地；Honcho 游标记录筛选后的消息条数 |
| 已处理 | 后端完成分析并保存分析产物后，更新自己的处理状态 | 由后端管理任务与结果；具体持久化方式待设计，不在采集目录另造 `processed.json` |

JSONL 是后台直接读取的持久材料来源；worker 根据材料范围、已登记任务和自身处理位置组织待办。通知或任务登记不表示分析完成；后台完成保存及校验后才推进处理位置。工具摘要也是队列条目，因此后台处理位置不能直接使用 rollout 正文消息的采集计数。

```text
~/.distillAI/
├── config.json
└── codex/
    ├── queue/
    │   └── <key>.jsonl
    └── cursors/
        └── <key>.json
```

`<key>.jsonl` 为 UTF-8 追加式队列，每行一个采集条目，可记录用户消息、助手消息或工具活动；`cursors/<key>.json` 保存采集进度，后台任务与处理状态由 M01 管理。key 与来源定位沿用[初版最小边界](#minimal-capture-boundaries)。队列保存的是筛选后的材料，不是完整 rollout 镜像，也不是语义摘要或用户掌握结论。

#### 已确认的采集到后台执行交接

统一运行数据根中的 `config.json` 管理产品运行参数；配置读取和 Web 修改入口集中见 [T02：统一配置与 Skill 读取](../01-runtime/design.md#configuration-management)。

2026-10-09，用户确认采集 Hook 同步执行，不配置 `async: true`。Hook 只完成必要的本地材料落盘、采集 cursor 保存和轻量任务通知，不等待后台接收确认、任务执行或 Agent 分析；Codex 的等待范围限于这段短时本地操作。

```text
Hook（同步）：读取新增材料 → 追加队列 → 保存采集 cursor → 轻量通知 worker → 返回
worker（异步）：扫描材料队列并登记新增范围 → 定期轮询任务队列 → 调度后台 Agent
→ Agent 分析并修改产品文件 → 程序校验 → 推进后台处理位置
```

通知用于加快发现新增材料；通知失败不阻塞 Codex，也不撤销已落盘材料。worker 启动、恢复及定期检查时根据持久队列和自身进度发现待办并补登记任务，重复通知复用同一材料范围的待办。后台离线或 Agent 崩溃不要求 Hook 等待恢复。

采用轻插件、重后端的架构：接入端保留 AI 工具适配、材料落盘和轻量通知；任务合并、调度、去重、重试与故障恢复集中在后台程序，语义分析由后台 Agent 执行，便于后续适配不同 AI 工具。Hook 仍需保证本地写入的必要完整性；采集补读依靠后续触发，不另建接入端常驻补采程序。

本项确认采集 Hook 的等待边界及 worker 本地接管方式；本轮注入筛选的同步等待见 D05。轻量通知参数和发送行为见[通知契约](#material-notification)，通信及轮询配置复用 M01，任务字段仍由 M01 定义，不新增上传批次与确认协议。

分析失败按 M01 的后台恢复规则处理，不推进处理位置，已落盘原始材料继续保留。采集失败不提前推进 cursor；重采可能性、尾部等待与异常增强范围遵循[初版最小边界](#minimal-capture-boundaries)，实际 Desktop 行为按 Q16 验证。
